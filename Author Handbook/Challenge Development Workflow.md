# Challenge Development Workflow

This workflow defines the DES authoring lifecycle from first idea to classroom release.

## 1. Idea

Start with a course topic that benefits from engineering judgement. Prefer topics where students can inspect a system, model a load, compare options, verify safety, or justify a design decision.

Author output:

- Topic area
- Target course and unit
- Intended Course Outcome
- Initial engineering question

## 2. Industry Scenario

Convert the topic into a realistic situation. Identify the product, user, operating condition, failure risk, design constraint, or client need.

Author output:

- Scenario paragraph
- Stakeholder
- Design or verification need
- Practical constraints

## 3. Project Charter

Define the student mission. The charter should clarify scope before content is written.

Author output:

- Problem statement
- Objectives
- Constraints
- Assumptions
- Deliverables
- Success criteria
- Required evidence

## 4. Engineering Activities

Break the work into activities that create learning evidence. Activities should progress logically from system understanding to calculation and decision.

Suggested sequence:

1. Observe or interpret the system.
2. Identify known and unknown values.
3. Draw or inspect the engineering model.
4. Select assumptions.
5. Apply relevant equations.
6. Check units and reasonableness.
7. Compare with allowable limits.
8. Make a recommendation.
9. Document the result.

## 5. Interactive Components

Choose DES components that support the activity. Do not add interaction for decoration.

For each component, document:

- Component purpose
- Student action
- Expected evidence
- Linked activity
- Assessment use

## 6. Assessment

Create a rubric before finalizing the challenge. Assessment should measure the intended outcome, not just task completion.

Assessment output:

- CCE marks
- Rubric criteria
- Performance levels
- CO, PO, PSO, WK, and Bloom mapping
- Required notebook or report evidence

## 7. Faculty Review

A second faculty member or coordinator reviews the challenge for correctness, alignment, feasibility, and compatibility.

Review checks:

- Technical accuracy
- Metadata completeness
- OBE, CCE, and WK alignment
- Student workload
- Clarity of instructions
- Platform compatibility

## 8. Student Pilot

Run the challenge with a small group before full release. Observe where students hesitate, misread instructions, misuse formulas, or produce weak evidence.

Pilot evidence:

- Completion time
- Common questions
- Misconceptions
- Submission quality
- Student feedback
- Faculty observations

## 9. Revision

Revise only challenge content and authoring documents. Keep the frozen platform unchanged.

Revision actions:

- Clarify unclear instructions.
- Adjust workload or estimated time.
- Improve hints without revealing answers.
- Correct technical errors.
- Update rubric descriptors.
- Record version changes.

## 10. Release

Release only after review and approval. The challenge should be ready for repeated classroom use.

Release requirements:

- Metadata complete
- Rubric approved
- Faculty notes complete
- Student-facing content proofread
- Interactive components checked
- Approval status set
- Version history updated
